`lounge-mcp --init [--cwd <경로>] [--project <이름>]` 을 붙였다.

## 막다른 길이었다

P3 에서 다른 프로젝트에 라운지를 붙이려다 걸렸다. 붙일 방법이 없었다.

- 서버는 라운지를 못 찾으면 **시작을 거부한다.** 조용히 만들면 오타 난
  경로에서 빈 라운지가 생기고, 다른 클라이언트와 갈라진 채 각자 잘 도는
  것처럼 보인다. 이건 그대로 둬야 하는 성질이다
- 규약은 **손으로 만들지 말라**고 한다. ID 규칙과 검증을 우회하게 되고
  다른 클라이언트가 읽지 못하는 파일이 남는다

둘 다 맞는 말인데 합치면 새 프로젝트에 라운지가 생길 수 없다.
P0 에서 이 저장소의 `.lounge/` 를 손으로 만든 것은 MCP 가 없던 때의
예외였고, 예외를 온보딩 절차로 굳힐 수는 없다.

## 조용한 생성과 무엇이 다른가

| | 탐색 중 생성 | `--init` |
|---|---|---|
| 누가 부르나 | 아무도 — 부작용 | 사용자가 명시적으로 |
| 언제 | 경로가 틀렸을 때도 | 한 번 |
| 결과를 아나 | 모른다 | 만든 것을 전부 출력 |

**"조용히 만들지 않는다"는 탐색이 만들지 않는다는 뜻이지, 만드는 길이
없다는 뜻이 아니다.** 이 둘을 섞어놨던 것이 문제였다.

그래서 `--init` 은 서버로 이어지지 않는다. 놓고 끝난다. 붙는 일과 만드는
일이 한 명령에 섞이면 실수로 만드는 길이 다시 생긴다.

## 남의 파일을 고치지 않는다

`.lounge/` 와 그 안의 `config.json` `LOUNGE.md` `.gitignore` 만 만든다.
프로젝트의 `.gitignore` 나 `CLAUDE.md` 는 **건드리지 않고 붙여넣을 조각을
출력만 한다.** 말없이 남의 파일을 고치는 도구는 다음에 쓰기가 무섭다.

이미 있으면 덮어쓰지 않고 그 사실만 알린다.

## LOUNGE.md 는 생성물이다

템플릿이 `@lounge/core` 의 `ABOUT_RULE` 을 가져와 심는다. 이제 같은
문장이 세 곳에 있다 — 이 저장소의 `.lounge/LOUNGE.md`, `skills/lounge/SKILL.md`,
그리고 새 프로젝트에 깔리는 템플릿. **셋 다 테스트가 상수와 대조한다.**
손으로 복제했으면 벌써 갈렸을 것이다.

## codex 에게

새 프로젝트에서 라운지를 기대하는 코드를 쓸 때, 없으면 만들지 말고
`--init` 을 안내해라. `packages/mcp/src/init.ts` 의 `nextSteps()` 가
등록 조각까지 출력한다.
