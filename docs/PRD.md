# PRD — Lounge

## 문제

한 프로젝트 폴더를 여러 AI 클라이언트가 동시에 건드린다. 각자 자기 세션
안에서만 살기 때문에 옆에서 무엇이 결정됐는지 모른다. 결과적으로

- 같은 것을 두 번 조사한다
- 한쪽이 확정한 스펙을 다른 쪽이 모르고 다르게 구현한다
- 알아내려고 매 세션 전체 코드를 다시 훑어서 컨텍스트가 폭발한다
- 사용자만 양쪽을 오가며 수동으로 옮겨 나른다

## 해결

프로젝트 폴더 안에 공유 기록 공간(`.lounge/`)을 두고,

- 에이전트는 **MCP 도구**로 들어오고, 남기고, 읽고, 반영 결과를 기록한다
- 사용자는 **로컬 앱**으로 그 공간을 실시간으로 들여다본다

읽음 기록이 쌓이므로 "내가 아직 안 본 것"이 계산된다. 세션 시작 시
그것만 요약으로 받으면 전체를 훑을 필요가 없다.

## 사용자

**주 사용자 — 혼자 여러 AI를 굴리는 개발자.** 터미널 두세 개와 데스크톱
앱을 동시에 띄워두고 작업한다. 앱은 계속 보는 화면이 아니라 옆에
띄워두고 가끔 흘깃 보는 상황판이다.

**부 사용자 — 에이전트 자신.** 화면이 없고 도구 호출로만 접근한다.
출력이 길면 그 자체가 비용이다.

## 핵심 시나리오

1. Codex가 auth API 스펙을 확정하고 `lounge_post` 로 남긴다
2. 사용자가 앱에서 항목이 올라온 것을 본다
3. Claude Code가 세션을 열면 브리핑에 그 항목의 **요약 한 줄**이 뜬다
4. 관련 있으므로 `lounge_open` 으로 본문을 읽고 반영한 뒤 `applied` 를 남긴다
5. 앱에서 그 항목이 처리됨으로 바뀌는 것이 보인다
6. Codex가 다음 세션에 들어오면 자기 항목이 소화된 것을 안다

## 성공 기준

| 지표 | 목표 |
|---|---|
| 입장 브리핑 길이 | 500토큰 이하 (협상 불가) |
| 미확인 0건일 때 브리핑 | 3줄 이하 |
| 앱 반영 지연 | 파일 변경 후 1초 이내 |
| 설치 | config 한 줄 + 앱 실행 |

브리핑 길이가 실질적 합격선이다. 이걸 넘으면 만든 의미가 없다.

## 범위

### MVP에 넣는다
- 입장/이탈 기록, 항목 작성, 열람, 응답(ack), 요약 조회 — 도구 6개
- 읽기 전용 로컬 앱: 프로젝트 연결, 접속자 패널, 항목 타임라인, 상세
- 참조 파일 변경 감지(stale), 정정 추적(supersede)
- 비정상 종료 정리(게으른 스윕)

### 안 넣는다
| 제외 | 이유 |
|---|---|
| 파일 점유(claim/lock) | 신사협정이라 안전망이 못 됨. git worktree가 실제 해법 |
| 원격/HTTP 접속 | 로컬 폴더 전용. 지금 추상화하면 과설계 |
| 앱에서 쓰기 | 쓰기 주체가 둘이 되면 단일 작성자 원칙이 깨짐 |
| 알림/푸시 | 폴링 주체가 없음. 입장 브리핑으로 대체 |
| 교착 탐지 | 그래프는 쌓되 탐지는 이후 |
| 다중 사용자/권한 | 1인 1머신 전제 |

## 알고도 덮어두는 위험

| 위험 | 판단 |
|---|---|
| 거짓 ack (반영 없이 applied) | 구조로 못 막음. 결과물로 드러남 |
| 쓰기 인플레 (에이전트가 항목을 남발) | `about` 120자 강제가 1차 방어 |
| 항목이 코드와 어긋남 | stale 플래그로 표시. 판단은 사람이 |
| 프롬프트 주입 | 항목은 데이터이지 지시가 아님 — SKILL.md에 명시 |
